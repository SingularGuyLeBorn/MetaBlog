# Skill 仓库设计规范

> 本规范适用于 `.skills/` 目录下所有 Skill 的设计、编写和维护。

---

## 什么时候优先选哪类 skill？

| 场景 | 优先 skill 类型 |
|------|---------------|
| 问产品文档 / 官方资料 | wiki 类 skill |
| 想优化 Prompt / 配置 / skill 本身 | 审查优化类 skill |
| 想把流程、结构、时序整理成图 | mermaid skill |
| 想把论文 / 仓库整理成报告 | 解读生成类 skill |
| 服务出问题、命令不会用、要排障 | 运维类 skill |
| 要把能力装到工具里、同步到多个目录 | 安装同步类 skill |

---

## 仓库设计原则

1. **description 是给模型看的触发规则，不只是简介**
   - 模型通过 description 决定是否调用该 skill
   - 必须写清「做什么 + 什么时候触发 + 不适用场景」

2. **SKILL.md 负责调度，细节尽量拆到 references / scripts / assets**
   - SKILL.md 只保留：适用边界、设计模式、Gotchas、工作流、输出要求
   - 长逻辑、模板、清单拆到子目录

3. **默认先交付初稿，不自动做超出用户预期的后续动作**
   - 不要擅自执行用户没明确要求的多步操作
   - 涉及高影响操作（写文件、删数据、发消息）必须先说明再执行

4. **能脚本化的重复动作，尽量不要只写成文字说明**
   - 有明确步骤的重复工作，写成可执行脚本放到 `scripts/`

5. **持续沉淀 Gotchas，降低误触发和翻车概率**
   - 每次使用后记录：什么情况下 skill 行为不符合预期、怎么避免

## 新增 skill 时建议遵循的规范

### Frontmatter 规范

只保留 `name` 和 `description` 两个字段：

```yaml
---
name: 文章管理
description: |
  管理 VitePress 博客文章，支持创建、读取、更新、删除和搜索。
  触发时机：用户提到"写文章""改文章""找文章""删文章"等。
  不适用：与文章无关的通用聊天。
---
```

description 必须同时写清：
- **做什么** — 一句话能力说明
- **什么时候触发** — 触发关键词 / 场景
- **不适用场景**（必要时）— 什么情况下不该触发，降低误匹配

### SKILL.md 内容优先级

按以下顺序编写：

1. **适用边界** — 这个 skill 管什么、不管什么
2. **设计模式** — 属于哪类（Tool Wrapper / Generator / Reviewer / Inversion / Pipeline）
3. **Gotchas** — 已知坑点、边界情况、常见误用
4. **工作流** — 接到任务后的处理步骤
5. **输出要求** — 最终交付物格式、必须包含的字段

### 长逻辑拆分

如果 skill 逻辑较长，优先拆到：

| 目录 | 用途 |
|------|------|
| `references/` | 规范、模板、清单、补充文档 |
| `scripts/` | 可执行脚本 |
| `assets/` | 固定模板、示例资源 |

示例结构：
```
.skills/my-skill/
├── SKILL.md           # 调度入口（短，只写工作流和边界）
├── references/
│   └── template.md    # 输出模板
├── scripts/
│   └── setup.sh       # 初始化脚本
└── assets/
    └── example.png    # 示例图
```

### 高影响操作门槛

如果 skill 涉及以下动作，必须明确写出**确认门槛**：
- 外部写操作（写文件、发消息、改配置）
- 自动复查或定时任务
- 删除或覆盖数据

确认门槛示例：
> 执行写操作前，必须向用户说明：修改内容、影响范围、回滚方式，等待用户确认后再执行。

### 审查/规划类 skill 默认流程

如果是审查或规划类 skill，默认遵循：

```
先审查 / 诊断 → 再出计划 → 确认后再修改
```

禁止未诊断直接给方案，禁止未确认直接执行修改。
