# Session 2026-05-04

## 问题发现

用户反馈多个 UI 问题：
1. 下拉箭头显示问题，所有下拉框样式混乱
2. 文章管理/触发器页面有重复的保存/取消按钮
3. 添加记忆的下拉框溢出但没有滚动条
4. 需要统一所有下拉框样式
5. 去掉 agent/chat 界面的 agent控制中心、系统控制台、日志监控、返回首页、删除按钮
6. 管理中心缺少 git 部分
7. 可用 Skills 列表文字溢出、框高度不够
8. SessionManager 中"全部 Agent"和"全部时间"文字需要精简

## 根因分析

1. **下拉框混乱**：项目中有多种下拉框实现（`DropdownSelect.vue`、`GlassSelect.vue`、原生 `<select>`），样式不统一，且 `DropdownSelect` 缺少下拉箭头图标
2. **重复按钮**：`AgentConfigPanel.vue` 底部始终显示保存/取消按钮，而其内部的 `TriggerPanel.vue` 也有自己的保存/取消按钮，导致触发器标签页出现两组按钮
3. **Skills 溢出问题**：`AgentConfigPanel.vue` 中 `.skill-item` 使用 `align-items: center`，`.skill-desc` 没有设置 `line-height`，导致文字可能被截断
4. **缺少 Git**：`GitManager.vue` 已实现但未被注册到 `AICenterPage.vue` 的管理中心导航中

## 方案选择

**统一方案**：
- 重新设计 `DropdownSelect.vue` 作为唯一标准下拉框组件
- 删除 `GlassSelect.vue`，所有使用处改为 `DropdownSelect`
- 将所有关键组件中的原生 `<select>` 替换为 `DropdownSelect`
- 在全局 CSS 中保持原生 `<select>` 的基础样式（作为后备）

**未选择的方案**：
- 保留 `GlassSelect` 并单独维护其样式 —— 会增加维护负担，且无法解决样式不统一问题
- 只修改 CSS 来统一原生 `<select>` —— 原生 `<select>` 的下拉菜单无法通过 CSS 自定义

## 追加修改（第二轮）

### 问题发现

1. 用户截图反馈"可用 Skills"界面描述文字被截断/溢出
2. 用户反馈"记忆分类下拉框溢出但没有滚动条" — 所有 DropdownSelect 都有这个问题
3. 用户反馈 Agents 和 MCP 左右 icon 不一致
4. 用户反馈重启服务后页面加载要 20+ 秒
5. 用户反馈 Agents 和 Skills 都是空的（0 个 Agent / 没有找到 Skills）

### 根因分析

1. **Skills 描述截断**：`.skill-info` 作为 flex item 没有设置 `min-width: 0`，导致长文本不会换行溢出
2. **下拉框无滚动条**：`DropdownSelect` 的 `.dropdown-menu` 使用 `position: absolute`，被祖先 `LiquidGlass` 的 `overflow: hidden` 裁剪，导致选项超出部分无法显示也无法滚动
3. **Icon 不一致**：AgentManager.vue 标题用 `users` 而左侧导航用 `bot`；MCPConfigPanel.vue 标题用 `cpu` 而左侧导航用 `plug`
4. **加载慢**：之前手动清理了 `node_modules/.vite` 缓存，导致 Vite 强制重新预构建所有依赖（`Forced re-optimization of dependencies`）。项目规模大（211 markdown + 93 Vue），dev 模式下浏览器需逐个加载模块
5. **Agents/Skills 为空**：`init()` 数据初始化原来只在 `AgentAdmin.vue` 的 `onMounted` 中调用。之前删除了 `Layout.vue` 中对 `AgentAdmin` 的引用，导致 `AgentAdmin` 不再渲染，`init()` 永远不会被执行，agents 和 skills 永远是空数组

### 方案选择

- **DropdownSelect 修复**：使用 `Teleport` 将下拉菜单传送到 body，配合 `fixed` 定位，彻底脱离 `LiquidGlass` 的裁剪上下文
- **数据加载修复**：在 `AICenterPage.vue` 的 `onMounted` 中调用 `init()`，确保进入 Manager 视图时自动加载数据

## 追加修改（第三轮）

### 问题发现

1. 用户要求"可用 Skills"从长条列表改为卡片网格
2. 用户要求使用懒加载，先打开界面，重的模块慢慢加载
3. 用户提醒不要手动清理 `node_modules/.vite`

### 根因分析

1. **长条列表**：`AgentConfigPanel.vue` 中 `.skills-list` 使用 `flex-direction: column`，每个 skill 是横向布局
2. **没有懒加载**：`src/theme/index.ts` 中所有组件都是同步 `import`，首屏会加载全部 93 个 Vue 组件 + 重型依赖（cytoscape、vditor、three 等）
3. **`optimizeDeps.force: true`**：`.vitepress/config.ts` 中设置了 `force: true`，导致 Vite **每次启动都强制重新预构建所有依赖**，这是加载 20+ 秒的**根本原因**（比清理缓存更严重）

### 方案选择

- **卡片网格**：`.skills-list` 改为 `grid` + `auto-fill`，每个 skill 垂直布局（图标在上、名称、描述）
- **组件级懒加载**：`src/theme/index.ts` 中 Pages 和重型 Feature 组件使用 `defineAsyncComponent`
- **模块级懒加载**：`AICenterPage.vue` 中 Manager 子面板使用 `defineAsyncComponent` + `import()`，配合 `<Suspense>` 显示加载状态
- **移除 `force: true`**：改为 `include: ["vue", "pinia", "@vueuse/core"]` 只预构建核心依赖

### 修改文件清单

| 文件 | 修改类型 | 说明 |
|------|---------|------|
| `src/theme/components/agent/AgentConfigPanel.vue` | 修改 | Skills 列表从长条改为卡片网格（grid + 垂直布局） |
| `src/theme/index.ts` | 修改 | Pages/Feature 大组件改为 `defineAsyncComponent` 异步加载 |
| `src/theme/components/pages/AICenterPage.vue` | 重写 | Manager 子面板全部改为 `defineAsyncComponent` 按需加载；添加 `<Suspense>` 加载状态 |
| `.vitepress/config.ts` | 修改 | `optimizeDeps.force: true` → `include: ["vue", "pinia", "@vueuse/core"]` |

### 验证结果

- Vite 配置修改后，dev server 启动不再显示 `Forced re-optimization of dependencies`
- 组件懒加载生效，首屏只加载必要模块，切换 Manager tab 时才加载对应面板

### 遗留问题

- `node_modules/.vite` 缓存已被清空，需要 dev server 运行一段时间后自动重建
- 部分重型依赖（cytoscape、vditor）在首次访问对应页面时仍需加载，但不会再阻塞首屏

## 追加修改（第四轮）

### 问题发现

用户要求：
1. `MessageBubble.vue` Markdown 标题（h1~h6）没有样式，需要添加 Star River 设计体系下的 heading 样式
2. 批量创建文档/搜索结果等大量内容不要堆在 message bubble 里，需要右侧抽屉/模态框展示
3. 错误码翻译必须精确到具体参数（"参数不合法" → "参数 X 的类型应为 Y，实际得到 Z"）
4. Markdown 转换器需要更详细的错误反馈
5. Skill 提示词要加入"不要大段输出到 message bubble"的约束
6. 任务连续性：Skill 要教 LLM 记录当前进度

### 根因分析

1. **Heading 无样式**：经检查，`MessageBubble.vue` 中 `.response-body :deep(h1~h6)` 样式**已存在**，但 compacted context 提示"已添加（待验证）"，实际上样式定义已完整
2. **批量结果堆积**：`BatchResultDrawer.vue` 和 `batchResultStore` 已存在，`ChatLayout` 也已引入，但**没有自动触发机制**。只有 `MessageBubble.vue` 中的手动 `stashContent`（基于消息长度阈值）
3. **错误码模糊**：整条链路都存在信息丢失：
   - 飞书 API 返回 `{ code, msg, error/field_violations }`（含具体字段）
   - `sendLarkResult` 翻译后返回 `{ code, msg, suggestion, original }`，**original 中有原始详情**
   - 但 `feishuDocAppend` 只读取 `result.msg` 和 `result.code`，**完全忽略了 `result.original` 和 `result.suggestion`**
   - `registry.ts` 的 `catch` 只保存 `error.message`
   - `toolStore.errorToolCall` 只接收 `error: string`
   - `toolStore.completeToolCall` **总是设置 `status = 'success'`**，即使 `result.success === false`
4. **Markdown 转换器无错误反馈**：`markdownToBlocks` 返回空数组时，`feishuDocAppend` 只说"缺少内容"，没有说明为什么转换为空
5. **Skill 缺少约束**：`.skills/feishu-assistant/SKILL.md` 没有要求 LLM 精简输出，也没有精确到参数的错误码映射表

### 方案选择

**错误精确化方案**：
- 增强 `ToolResult` 类型，新增 `details` 字段（结构化错误详情）
- 增强 `createErrorResult`，支持 `details` 参数
- 后端 `lark-error-translator.ts` 新增 `extractErrorDetails` 函数，从飞书原始响应中提取 `field`、`fieldMessage`、`fieldViolations`、`msgDetail`
- 后端 `lark.ts` 的 `sendLarkResult` 在返回中包含 `details`
- 前端 `feishuDocAppend` 读取 `result.details` 和 `result.suggestion`，构建精确到参数的错误信息
- `registry.ts` 的 `executeToolWithRecord` 保留完整错误结构到 `record.result`
- `toolStore.completeToolCall` 根据 `result.success` 自动判断状态（之前总是 success）

**批量结果自动收纳方案**：
- 在 `chatStore.ts` 的 `onToolCallComplete` 回调中，检查工具结果大小
- 如果工具名包含 search/list/batch/create/append 且结果 >3000 字符或数组 >10 项，自动推送到 `batchResultStore`
- AI 消息中只保留摘要

|------|---------|------|
| `src/theme/tools/types.ts` | 修改 | `ToolResult` 新增 `details?: Record<string, any>`；`createErrorResult` 新增 `details` 参数 |
| `server/utils/lark-error-translator.ts` | 修改 | 新增 `extractErrorDetails` 导出函数，从飞书原始响应中提取 field/fieldViolations/msgDetail |
| `server/routes/external/lark.ts` | 修改 | `sendLarkResult` 返回中添加 `details: extractErrorDetails(result)` |

## 追加修改（第五轮）

### 问题发现

用户提出两个新功能需求：
1. **Skill 自发现**：AI 能自己去找 skill，调用工具存到本地，调用更新 skill 信息工具更新项目信息，下次能自己加载
2. **增强图片处理能力**

### 根因分析

**Skill 自发现：**
- 现有 `manageSkill` 工具只有 `create/list/get/update/delete`，没有从外部导入 skill 的能力
- `getAllSkills` 只读取不刷新缓存，返回完整 content（token 占用大）
- System Prompt 中没有告诉 AI：当找不到合适 skill 时，可以去网上导入
- 导入 skill 后，前端 `agentStore` 的缓存不会自动刷新，新 skill 不会立即出现在可用列表中

**图片处理：**
- 当前只有 OCR 和飞书/语雀图片插入，没有文生图能力
- Vision 模型（kimi-k2.5）可以分析图片，但没有专门的结构化图片描述工具

### 方案选择

**Skill 自发现方案：**
1. 扩展 `manageSkill`：增加 `import` action，从 URL 下载 SKILL.md，解析 YAML frontmatter，调用 `/api/skills` 创建
2. 新增 `refreshSkillRegistry` 工具：调用 `/api/skills` 获取列表，刷新 `agentStore` 缓存，返回精简摘要（不含 content）
3. 将 `refreshSkillRegistry` 加入 `CORE_TOOL_NAMES`（始终暴露）
4. 修改 `buildSystemPrompt`：加入 Skill 自发现工作流说明

**图片增强方案：**
1. 新增 `generateImage` 工具：基于 Pollinations.ai 免费文生图 API（无需 key），返回图片直链

## 追加修改（第八轮）

### 问题发现

用户反馈：
1. "光写参数不合法不行，得写清楚什么参数不合法"
2. Markdown 转换器需要更详细的错误反馈
3. 要求极大增强错误码翻译器，每一个错误码都得精确到输入字段

### 根因分析

- 后端 `lark-error-translator.ts` 虽然覆盖了主要错误码，但 `message` 字段仍较笼统（如"参数不合法"），没有利用飞书原始响应中的 `error.field`、`error.message`、`msg_detail` 等字段
- 后端 `sendLarkResult` 调用 `translateLarkError` 时只传了 `msg` 和 `code`，没有传 `original`（完整原始响应）
- 前端 `larkApi` 返回的错误中，`data.msg` 是简短翻译，调用点 `createErrorResult(result.msg, ...)` 只能拿到简短消息
- `markdownToBlocks` 没有输入验证和诊断信息，转换失败时只说"转换结果为空"
- 前端 7 个飞书工具文件（doc/wiki/im/image/permission/user/token）中，几十个错误处理点都只用了 `result.msg`

**核心方案：三层增强**

1. **后端翻译器增强**：`translateLarkError` 接收 `original` 参数，新增 `buildPreciseMessage` 函数，从 `details` 中提取 `field`/`fieldMessage`/`actualValue`/`expected`/`fieldViolations`/`msgDetail`，构建精确到字段的错误消息
2. **后端发送层增强**：`sendLarkResult` 传递 `original` 给翻译器，翻译结果中的 `details` 直接复用
3. **前端 API 层增强**：在每个 `larkApi` 函数中，返回前自动把 `data.details` 中的字段信息合并到 `data.msg` 中。这样所有调用点 `createErrorResult(result.msg, ...)` 自动获得增强信息，无需逐个修改调用点

**未选择的方案**：
- 逐个修改 50+ 个错误处理点：改动量极大，易遗漏
- 在 `createErrorResult` 中自动处理：会侵入通用类型层，耦合度过高

**Markdown 转换器增强方案**：
- 新增 `markdownToBlocksWithDiagnostics` 函数，返回 `{ blocks, warnings, stats }`
- 增加输入验证（null/undefined/非字符串/超长内容）
- 增加空 block 过滤的警告记录
- `feishuDocAppend` 使用诊断版本，转换失败时返回具体原因

## 追加修改（第十轮）— 找到真正的根因并修复

### 问题发现

用户连续三次反馈"光写参数不合法不行，得写清楚什么参数不合法"。

前两轮虽然做了大量增强（inferDetailsForCode、buildPreciseMessage、前端 details 合并），但用户仍然不满意。

**通过子代理深入审查，发现真正的根因。**

### 根因分析

**根因 1：inferDetailsForCode 被短路**

`extractErrorDetails` 会提取 `requestParams`（第85-91行）：
```typescript
if (original.request_params && typeof original.request_params === 'object') {
  details.requestParams = Object.keys(original.request_params).reduce(...)
}
```

当飞书返回的 original 中**只有 `request_params` 而没有 `error.field`/`field_violations`/`msg_detail`** 时，`details` 变成 `{ requestParams: {...} }`。

这个对象非空，因此 `if (!details || Object.keys(details).length === 0)` 条件为 **false**，**跳过了 `inferDetailsForCode`**。

`buildPreciseMessage` 只消费 `fieldViolations`/`field`/`msgDetail`/`rawError`，**完全不认识 `requestParams`**。

结果：`buildPreciseMessage("飞书文档 API 参数不合法", { requestParams: {...} })` 只返回 `"飞书文档 API 参数不合法"`，没有任何字段信息。

**这就是用户反复看到"参数不合法"的最主要根因。**

**根因 2：前端7个文件重复追加 details**

后端 `sendLarkResult` 已经把 details 精确拼接到 `msg` 中了。前端 `larkApi` 又做了一次同样的拼接：
```typescript
if (data.code !== 0 && data.details) {
  if (d.field) { data.msg = data.msg + ' | 参数 "' + d.field + '"...' }
}
```
导致信息重复、消息冗长混乱。

**根因 3：feishuDocAppend 硬编码覆盖精确消息**
```typescript
if (code === 1770033) { reason = '单个文本块内容超过 10000 字符限制'; ... }
else if (code === 99992402) { reason = '请求字段校验失败'; ... }
```
`reason = '请求字段校验失败'` 极其笼统，直接丢弃了 `result.msg` 中后端翻译的精确字段信息。

### 方案选择

**修复 1：修改 translateLarkError 的 details 合并逻辑**

将原来的"空时 fallback"改为"永远合并"：
```typescript
const extractedDetails = extractErrorDetails(original);
const inferredDetails = inferDetailsForCode(bizCode);
const details: Record<string, any> = {};
if (inferredDetails) Object.assign(details, inferredDetails);   // 推断的兜底
if (extractedDetails) Object.assign(details, extractedDetails); // 提取的优先覆盖
```

这样即使 `extractedDetails` 只有 `requestParams`，`inferredDetails` 中的 `field`/`expected`/`fieldMessage` 也会被保留。

**修复 2：移除前端7个文件的重复 details 追加**

后端已经精确拼接，前端不需要再做。移除后消息更干净。

**修复 3：修复 feishuDocAppend 硬编码**

只覆盖 `suggestion`，保留 `result.msg`（已包含后端翻译的精确字段信息）。
