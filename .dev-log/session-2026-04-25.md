## 任务 2：严查发现 3 个致命命名不一致

### 问题发现

用户连续 4 次要求"严查". 我启动了 3 个并行审计子代理,同时自己手动审查. 发现了**3 个致命问题**：

#### 问题 2.1：后端 `toolRegistry` 键是 snake_case,前端传 camelCase

```
前端 callGitHubTool('githubGetRepo')
    ↓
后端查找 toolRegistry['githubGetRepo'] → ❌ 不存在
    只有 toolRegistry['github_get_repo']
```
→ **34 个工具全部会返回 `Unknown tool`**

#### 问题 2.2：前端 `registry.getTool()` 同样不匹配

```
LLM 返回 toolCall.function.name = 'githubGetRepo'
    ↓
getTool('githubGetRepo') → Map key 是 'github_get_repo' → ❌
```

#### 问题 2.3：渐进式披露过滤永远匹配不上

```
availableTools = ['github_get_repo']  (snake_case)
d.function.name = 'githubGetRepo'     (camelCase)
includes() → false → 工具无法激活
```

### 根因分析

- 后端 `github-tool-executor.ts` 的函数名和 registry 键使用 snake_case(如 `github_get_repo`)
- 前端 `ToolDefinition.function.name` 使用 camelCase(如 `githubGetRepo`)
- 前端 `src/theme/tools/index.ts` 注册名使用 snake_case(如 `github_get_repo`)
- **三个地方的命名风格不一致**

**是否复发**：是. 这个问题在重构前就已存在,只是之前前端直接调 GitHub API(不走后端 registry),所以没暴露. 重构后前端走 `callGitHubTool` → 后端 `executeGitHubTool` → `toolRegistry`,命名差异才暴露. 

### 方案选择(反复！)

| 轮次 | 方案 | 说明 | 结果 |
|------|------|------|------|
| 第 1 轮 | normalize 兼容层 | 前后端都加 `normalizeToolName()`：camelCase → snake_case | ❌ **用户明确拒绝**："不要这样兼容吧" |
| 第 2 轮 | 全部 snake_case | 把前端 Def.name 和注册名改为 snake_case,删除兼容层 | ❌ **用户拒绝**："我喜欢 camelCase" |
| 第 3 轮 | **全部 camelCase** | 后端函数名、registry 键、ok/err toolName 全部改为 camelCase;前端注册名改为 camelCase;删除所有兼容层 | ✅ **用户接受** |

### 实现过程(第 3 轮 - 最终方案)

1. **前端 6 个 GitHub 文件**：Def.name + executor toolName 统一为 camelCase
2. **后端 `github-tool-executor.ts`**：
   - 34 个函数名 `github_get_repo` → `githubGetRepo`
   - 34 个 registry 键同步改为 camelCase
   - 所有 `ok()`/`err()` 的 toolName 参数改为 camelCase
   - 删除 `normalizeToolName` 函数和 fallback 逻辑
3. **前端 `src/theme/tools/index.ts`**：34 个 GitHub 注册名改为 camelCase
4. **前端 `src/theme/tools/registry.ts`**：删除 `normalizeToolName` 和 `getTool`/`hasTool` 的 fallback
5. **前端 `src/theme/api/services/aiService.ts`**：删除渐进式披露过滤中的 normalize 逻辑

## 关键决策记录

### ADR：GitHub 工具命名统一为 camelCase

**状态**：已通过(用户确认)

**上下文**：
- 后端函数名和 registry 键原为 snake_case(`github_get_repo`)
- 前端 Def.name 和 executor 函数名为 camelCase(`githubGetRepo`)
- 前端注册名为 snake_case(`github_get_repo`)
- 三处不一致,导致工具调用链断裂

**决策**：
全部统一为 **camelCase**：
- 后端函数名：`githubGetRepo`
- 后端 registry 键：`githubGetRepo`
- 前端 Def.name：`githubGetRepo`
- 前端注册名：`githubGetRepo`
- 删除所有 normalize 兼容层

**后果**：
- 正面：命名一致,无需兼容层,调用链清晰
- 负面：与 `ToolDefinition` 接口注释中的 "使用 snake_case" 建议冲突
- 风险：未来开发者可能误用 snake_case,需 code review 把关

**替代方案**：
- 全部 snake_case：被用户拒绝("我喜欢 camelCase")
- normalize 兼容层：被用户拒绝("不要这样兼容吧")

## 任务 6：聊天体验综合优化

### 问题发现(用户反馈 + 截图分析)

用户提交了 5 个改进需求 + 1 个公式渲染严重 bug：

1. **消息队列**：AI 执行期间无法发送新消息(当前逻辑直接阻塞)
2. **@ 引用文章范围有限**：只扫描 `docs/` 顶层,`recursive=true` 参数被后端忽略
3. **`/` Skill 弹窗为空**：弹窗显示"没有找到匹配的技能"
4. **图片上传 + 多模态提示**：需要明确告知当前模型是否支持多模态
5. **公式反斜杠过度转义**：AI 输出 `\\\pi`(5 个反斜杠),飞书文档公式渲染完全损坏

### 根因分析

**公式问题(P0)**：
- 系统提示词要求 AI 写 `\\pi`(JSON 双重转义)
- 但 AI 在 Function Calling 中生成的 JSON 会**再次**被框架序列化
- 结果：`\\pi` → JSON 序列化 → `\\\\pi` → 飞书看到 `\\pi` → 无法识别
- 加上 Markdown 代码块示例中的 `\\pi` 被 AI 直接复制,导致层层加码

**Skill 弹窗为空(P1)**：
- `ChatLayout` → `ChatInput` → `MentionInput` 的 props 链条中,`skills` 数组**从未被传入**
- `MentionInput` 的 `skills` prop 默认值为空数组 `[]`
- 过滤逻辑对空数组过滤,结果永远为 0

**@ 引用范围有限(P1)**：
- `loadArticles` 调用 `/api/files/list?path=docs&recursive=true`
- 但 `files.ts` 的 `list` handler **不支持 recursive 参数**
- 实际只返回 `docs/` 顶层文件

**消息阻塞(P2)**：
- `ChatLayout.handleSend`：`if (isStreaming.value) return`
- `ChatInput.canSend`：`return ... && !props.isStreaming`
- 双重阻塞,导致 AI 执行期间用户完全无法交互

### 修复方案与实现

#### 1. 公式反斜杠(P0)

**系统提示词** (`src/theme/skills/promptBuilder.ts`)：
- 删除红线 #3 "禁止 JSON 参数中使用未转义反斜杠"
- 删除所有带双重反斜杠的代码块示例
- 改为："你只需写标准 LaTeX 语法(如 `\pi`、`\frac`),框架会自动处理 JSON 序列化"
- 示例改为纯文本展示：`$E = mc^2$`、`$\pi$`、`$\frac{a}{b}$`

**飞书 SKILL.md** (`.skills/feishu-assistant/SKILL.md`)：
- 添加 "重要提醒" 区块：明确告诉 AI 不需要双重转义
- 添加错误自查项：❌ `\\pi` → ✅ `\pi`

#### 2. Skill 弹窗(P1)

- `ChatLayout.vue`：解构 `skills: allSkills`,绑定 `:skills="allSkills"` 传给 `ChatInput`
- `ChatInput.vue`：添加 `skills?: Skill[]` prop,绑定 `:skills="skills"` 传给 `MentionInput`
- `MentionInput.vue`：已支持 `skills` prop,无需修改

#### 3. @ 引用文章(P1)

- 该 API 递归扫描 `ALLOWED_SECTIONS`(posts, knowledge, resources),返回 `{ path, title, section }`
- UI 美化：添加 `section-tag` 显示文章所属板块,增大 dropdown 高度到 260px

#### 4. 消息队列(P2)

**chatStore.ts**：
- 新增 `pendingMessages` ref(按 session 存储队列)
- `sendMessage` 添加 `_isQueued` 内部参数：
  - `_isQueued = false` 且 `isStreaming`：创建用户消息显示在 UI,加入 `pendingMessages`,返回 true
  - `_isQueued = true`：复用最后一个没有 `aiVersions` 的消息组,直接创建 AI 响应并调用 `chatStream`
- `onComplete` / `onError` / `catch`：消费队列下一条消息,调用 `sendMessage(..., true)`

**ChatLayout.vue**：`handleSend` 去掉 `isStreaming.value` 检查

#### 5. 图片上传多模态提示(P2)
