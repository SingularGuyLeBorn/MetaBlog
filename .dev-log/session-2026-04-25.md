## 任务 2：严查发现 3 个致命命名不一致

### 问题发现

用户连续 4 次要求"严查"。我启动了 3 个并行审计子代理，同时自己手动审查。发现了**3 个致命问题**：

#### 问题 2.1：后端 `toolRegistry` 键是 snake_case，前端传 camelCase

```
前端 callGitHubTool('githubGetRepo')
    ↓
后端查找 toolRegistry['githubGetRepo'] → ❌ 不存在
    只有 toolRegistry['github_get_repo']
```
→ **34 个工具全部会返回 `Unknown tool`**

#### 问题 2.2：前端 `registry.getTool()` 同样不匹配

```
LLM 返回 toolCall.function.name = 'githubGetRepo'
    ↓
getTool('githubGetRepo') → Map key 是 'github_get_repo' → ❌
```

#### 问题 2.3：渐进式披露过滤永远匹配不上

```
availableTools = ['github_get_repo']  (snake_case)
d.function.name = 'githubGetRepo'     (camelCase)
includes() → false → 工具无法激活
```

### 根因分析

- 后端 `github-tool-executor.ts` 的函数名和 registry 键使用 snake_case（如 `github_get_repo`）
- 前端 `ToolDefinition.function.name` 使用 camelCase（如 `githubGetRepo`）
- 前端 `src/theme/tools/index.ts` 注册名使用 snake_case（如 `github_get_repo`）
- **三个地方的命名风格不一致**

**是否复发**：是。这个问题在重构前就已存在，只是之前前端直接调 GitHub API（不走后端 registry），所以没暴露。重构后前端走 `callGitHubTool` → 后端 `executeGitHubTool` → `toolRegistry`，命名差异才暴露。

### 方案选择（反复！）

| 轮次 | 方案 | 说明 | 结果 |
|------|------|------|------|
| 第 1 轮 | normalize 兼容层 | 前后端都加 `normalizeToolName()`：camelCase → snake_case | ❌ **用户明确拒绝**："不要这样兼容吧" |
| 第 2 轮 | 全部 snake_case | 把前端 Def.name 和注册名改为 snake_case，删除兼容层 | ❌ **用户拒绝**："我喜欢 camelCase" |
| 第 3 轮 | **全部 camelCase** | 后端函数名、registry 键、ok/err toolName 全部改为 camelCase；前端注册名改为 camelCase；删除所有兼容层 | ✅ **用户接受** |

### 实现过程（第 3 轮 - 最终方案）

1. **前端 6 个 GitHub 文件**：Def.name + executor toolName 统一为 camelCase
2. **后端 `github-tool-executor.ts`**：
   - 34 个函数名 `github_get_repo` → `githubGetRepo`
   - 34 个 registry 键同步改为 camelCase
   - 所有 `ok()`/`err()` 的 toolName 参数改为 camelCase
   - 删除 `normalizeToolName` 函数和 fallback 逻辑
3. **前端 `src/theme/tools/index.ts`**：34 个 GitHub 注册名改为 camelCase
4. **前端 `src/theme/tools/registry.ts`**：删除 `normalizeToolName` 和 `getTool`/`hasTool` 的 fallback
5. **前端 `src/theme/api/services/aiService.ts`**：删除渐进式披露过滤中的 normalize 逻辑

## 关键决策记录

### ADR：GitHub 工具命名统一为 camelCase

**状态**：已通过（用户确认）

**上下文**：
- 后端函数名和 registry 键原为 snake_case（`github_get_repo`）
- 前端 Def.name 和 executor 函数名为 camelCase（`githubGetRepo`）
- 前端注册名为 snake_case（`github_get_repo`）
- 三处不一致，导致工具调用链断裂

**决策**：
全部统一为 **camelCase**：
- 后端函数名：`githubGetRepo`
- 后端 registry 键：`githubGetRepo`
- 前端 Def.name：`githubGetRepo`
- 前端注册名：`githubGetRepo`
- 删除所有 normalize 兼容层

**后果**：
- 正面：命名一致，无需兼容层，调用链清晰
- 负面：与 `ToolDefinition` 接口注释中的 "使用 snake_case" 建议冲突
- 风险：未来开发者可能误用 snake_case，需 code review 把关

**替代方案**：
- 全部 snake_case：被用户拒绝（"我喜欢 camelCase"）
- normalize 兼容层：被用户拒绝（"不要这样兼容吧"）

## 本次 session 的失误记录

1. **PowerShell 批量替换导致函数名混乱**：第一次用 `$replacements` 批量替换前端文件时，将 camelCase 函数名错误替换为 snake_case，导致 `index.ts` 导入失败。
2. **文件损坏**：删除 Lark 重复路由时，`Set-Content -NoNewline` 把 `lark.ts` 变成了一整行，随后 prettier/TS printer 无法完全恢复，导致文件内容丢失。

**教训**：
- 批量替换后必须立即验证文件内容（读关键行）
- 删除代码块时，不要用 `Set-Content -NoNewline` 处理数组拼接
- 操作关键文件前，先确认 git 跟踪状态（`lark.ts` 是 `??` 未跟踪，无法 `git checkout` 恢复）
