# MetaBlog 开发日志规范

> **核心原则**：零隐藏。所有思考过程、错误尝试、回滚操作都必须记录。用户有权知道发生了什么。

---

## 为什么需要这个？

作为 Autonomous Software Engineer，我在执行过程中会：
- 调研多个方案后选其一
- 写代码后发现不对再改
- 测试时发现边界情况
- 甚至偶尔引入 regression

这些过程**不能藏在脑子里**。记录下来的好处：
1. **可追溯**：3 天后用户问"当时为什么这样改"，能查到
2. **防复发**：记录"这个问题之前犯过，原因是 xxx"
3. **可控感**：用户能看到每一步在做什么，不用猜
4. **知识沉淀**：新接手的开发者能快速理解项目演进

## 文件结构

```
.dev-log/
├── README.md                    # 本文件
├── session-YYYY-MM-DD.md        # 每次交互的完整记录(主日志)
├── session-YYYY-MM-DD-partN.md  # 同一天的后续交互
└── decisions/                   # 关键架构决策(ADR)
    ├── 001-context-truncation.md
    ├── 002-skill-system-lod.md
    └── ...
```

## Session 日志模板

**规则(用户确认版)**：
- ✅ 同一天的所有交互**追加到同一个 session 文件**，不新建 part
- ✅ **不加代码 diff**，保持可读性(只记录改了哪些文件、关键逻辑)
- ✅ **必须记录尝试但失败的方案**(用户特别强调，不能藏)
- ✅ 记录用户原话、调研来源、方案对比、验证结果
- ✅ 记录是否复发(关联历史日志)

每个 session 文件必须包含以下章节：

```markdown
# 开发日志 - YYYY-MM-DD

> 维护规则：每次交互后追加更新。

---

## 会话主题
[一句话概括这次交互的核心目标]

---

## 任务 N：任务名称

### 问题发现
[发现了什么问题，现象是什么，用户的原话或报错信息]

### 根因分析
[为什么会这样，追溯到代码的哪一层，之前是否有类似问题]

### 方案选择
[考虑过哪些方案，列 pros/cons，为什么最终选这个]

### 实现过程
[具体改了什么，关键代码片段，修改顺序]

### 修改文件清单
| 文件 | 修改类型 | 说明 |
|------|---------|------|

### 验证结果
[测试通过/失败，现象，截图或日志]

### 是否复发
[旧问题是否彻底解决，潜在复发点，相关 issue/PR]

### 遗留问题
[没做完的、需要后续跟进的]

---

## Git 状态
[哪些文件改了，是否已提交，commit hash]

---

## 待办
[按优先级排列的后续任务]

---

## 关键决策记录
[需要长期存档的决策，会同步到 decisions/ 目录]
```

---

## 必须记录的内容

✅ **必须写**：
- 用户提出的原始需求(原话或摘要)
- 我调研了哪些资料(链接、来源)
- **尝试过哪些方案、为什么失败、最终为什么选这个**
- 具体改了哪些文件、关键逻辑(不加 diff)
- 测试验证的过程和结果
- 是否引入了 regression
- 是否复发了之前的问题

❌ **不能藏**：
- "我试了一下发现不行然后改了另一种" → **两种都要记录，失败原因写清楚**
- "这个 bug 之前修过但又出现了" → 必须关联到之前的日志
- "代码看起来没问题但不确定" → 记录不确定性

## ADR(架构决策记录)

当做出影响架构的长期决策时，需要在 `decisions/` 创建独立文件：

```markdown
# ADR-XXX: 决策标题

## 状态
[提议 / 已通过 / 已废弃]

## 上下文
[当时面临什么问题，约束条件是什么]

## 决策
[选择了什么方案]

## 后果
[正面影响 / 负面影响 / 风险]

## 替代方案
[考虑过但没选的，以及为什么]
```

## 维护责任

- **我(AI)**：每次交互后主动更新 session 日志
- **用户**：review 日志是否准确，补充业务上下文
- **双方**：定期归档旧日志，更新待办状态
