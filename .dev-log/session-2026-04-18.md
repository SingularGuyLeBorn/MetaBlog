### 问题发现

```
Search API not configured

```

用户要求零成本方案，不需要 API Key、不需要信用卡。

### 方案选择

| 方案 | 成本 | 质量 | 决策 |
|------|------|------|------|
| Brave Search API | 需信用卡 | 高 | ❌ 不符合要求 |
| Tavily API | 免费额度1000次/月 | 高 | 备选 |
| DuckDuckGo HTML 抓取 | 完全免费 | 中等 | ✅ 默认方案 |
| Bing API | 需 API Key | 高 | 备选 |

**选择 DuckDuckGo HTML 版**（`https://html.duckduckgo.com/html/?q=query`）：
- 无需 API Key
- 支持中文搜索（`&kl=zh-cn`）
- 通过现有 `/api/proxy/fetch` 后端代理抓取，绕过 CORS

### 实现过程

**第一步：搜索模块架构设计**

用户反馈"搜索逻辑不应该塞在 executors.ts 里，文件会臃肿"。因此采用模块化设计：

```
src/theme/tools/network/
├── definitions.ts          # 工具定义
├── executors.ts            # 薄层执行器（只做参数校验和结果包装）
├── index.ts                # 统一导出
└── search/
    ├── index.ts            # searchWeb() 统一入口
    ├── types.ts            # SearchResult, SearchEngine, SearchOptions
    ├── utils.ts            # proxyFetchText, formatSearchResults, stripHtml
    └── duckduckgo.ts       # DuckDuckGo 引擎实现
```

**第二步：HTML 解析策略**

DuckDuckGo HTML 版的结构：
```html
<div class="result">
  <a class="result__a" href="/l/?uddg=https%3A%2F%2Fexample.com">标题</a>
  <a class="result__url">example.com</a>
  <a class="result__snippet">摘要文本...</a>
</div>
```

两个技术挑战：
1. **链接是重定向 URL**：`href="/l/?uddg=..."` 需要解码 `uddg` 参数
2. **HTML 解析鲁棒性**：DuckDuckGo 可能随时改结构

**解决方案**：双模式解析
- **主模式**：浏览器环境用 `DOMParser` + `querySelectorAll`（最可靠）
- **降级模式**：`DOMParser` 失败时用正则解析（保证不崩溃）

**第三步：代码实现**

`duckduckgo.ts` 核心逻辑：
```typescript
function parseResults(html: string): SearchResult[] {
  // 主模式：DOMParser
  const parser = new DOMParser();
  const doc = parser.parseFromString(html, 'text/html');
  const resultElements = doc.querySelectorAll('.result');
  // ... 提取 title, url, snippet
  
  // 降级模式：正则
  const blockRegex = /<div[^>]*class="result[^"]*"[^>]*>([\s\S]*?)<\/div>.../gi;
  // ...
}
```

URL 解码逻辑：
```typescript
function decodeDuckDuckGoUrl(url: string): string {
  if (url.startsWith('/l/?')) {
    const uddg = new URLSearchParams(url.slice(3)).get('uddg');
    if (uddg) return decodeURIComponent(uddg);
  }
  if (url.startsWith('/')) {
    return 'https://duckduckgo.com' + url;
  }
  return url;
}
```

## 任务 3：Agent Runner 自主执行系统设计文档

### 需求分析

用户要求设计"自主 Agent"的两个模式：
1. **心跳模式 A**：单个 Agent 定时被唤醒，由系统发送命令（即 Cron 直接调度）
2. **心跳模式 B**：系统定时唤醒一个调度器 Agent，该 Agent 接受用户任务，启动其他 Agent 执行，并汇总报告

用户问："哪个可保留？"

### 架构分析

**模式 A（Direct）本质**：系统 Cron → 唤醒指定 Agent → Agent 直接执行预设任务
**模式 B（Orchestrate）本质**：系统 Cron → 唤醒调度器 Agent → 调度器分析任务队列 → 分解子任务 → 分发执行 → 汇总报告

**关键洞察**：两个模式不是互斥的，是**互补的架构层**。

| 维度 | 模式 A (Direct) | 模式 B (Orchestrate) |
|------|----------------|---------------------|
| 触发源 | Cron 预设 | 用户提交的动态任务队列 |
| 调度决策 | 无（直接执行） | LLM 运行时分析分解 |
| 执行开销 | 低 | 高（调调度器 + 多个执行 Agent） |
| 错误隔离 | 好（单 Agent 失败不影响其他） | 调度器是单点 |
| 任务分解 | 无（预先拆分） | 自动（LLM 动态分解） |
| 适用比例 | ~80% 的简单定时任务 | ~20% 的复杂任务 |

**结论**：两个都保留。
- 模式 A 处理 **80% 的简单定时任务**（早报、备份、RSS 监控），高效、低成本
- 模式 B 处理 **20% 的复杂用户任务**（自然语言提交、多 Agent 协作），智能、灵活

### 设计产出

**文档**：`docs-internal/agent/agent-runner-design.md`（570 行）

包含：
1. 架构总览图
2. 两种模式的详细执行流程
3. 数据模型（AgentSchedule、QueuedTask、SubTask）
4. 系统调度器 + Agent Runner 执行引擎的伪代码
5. 调度器 Agent 的完整 Prompt 模板（任务分析阶段 + 结果汇总阶段）
6. 状态机（固定任务 Agent + 编排任务）
7. 与现有系统的集成方案（复用 SchedulerTool、TaskManager、agentStore、aiService）
8. 实现路径（4 个 Phase，~3 周）
9. 风险与对策（LLM 成本高、调度器单点、并发竞争、死锁）

## 任务 3：Agent Runner 自主执行系统设计文档

### 需求分析

用户要求设计"自主 Agent"的两个模式：
1. **心跳模式 A**：单个 Agent 定时被唤醒，由系统发送命令（即 Cron 直接调度）
2. **心跳模式 B**：系统定时唤醒一个调度器 Agent，该 Agent 接受用户任务，启动其他 Agent 执行，并汇总报告

用户问："哪个可保留？"

### 架构分析

**模式 A（Direct）本质**：系统 Cron → 唤醒指定 Agent → Agent 直接执行预设任务
**模式 B（Orchestrate）本质**：系统 Cron → 唤醒调度器 Agent → 调度器分析任务队列 → 分解子任务 → 分发执行 → 汇总报告

**关键洞察**：两个模式不是互斥的，是**互补的架构层**。

| 维度 | 模式 A (Direct) | 模式 B (Orchestrate) |
|------|----------------|---------------------|
| 触发源 | Cron 预设 | 用户提交的动态任务队列 |
| 调度决策 | 无（直接执行） | LLM 运行时分析分解 |
| 执行开销 | 低 | 高（调调度器 + 多个执行 Agent） |
| 错误隔离 | 好（单 Agent 失败不影响其他） | 调度器是单点 |
| 任务分解 | 无（预先拆分） | 自动（LLM 动态分解） |
| 适用比例 | ~80% 的简单定时任务 | ~20% 的复杂任务 |

**结论**：两个都保留。
- 模式 A 处理 **80% 的简单定时任务**（早报、备份、RSS 监控），高效、低成本
- 模式 B 处理 **20% 的复杂用户任务**（自然语言提交、多 Agent 协作），智能、灵活

### 设计产出

**文档**：`docs-internal/agent/agent-runner-design.md`（570 行）

包含：
1. 架构总览图
2. 两种模式的详细执行流程
3. 数据模型（AgentSchedule、QueuedTask、SubTask）
4. 系统调度器 + Agent Runner 执行引擎的伪代码
5. 调度器 Agent 的完整 Prompt 模板（任务分析阶段 + 结果汇总阶段）
6. 状态机（固定任务 Agent + 编排任务）
7. 与现有系统的集成方案（复用 SchedulerTool、TaskManager、agentStore、aiService）
8. 实现路径（4 个 Phase，~3 周）
9. 风险与对策（LLM 成本高、调度器单点、并发竞争、死锁）

## 任务 6：上下文截断策略重构 + 开发日志规范建立

**时间**：2026-04-18 会话后半段

**用户触发**：质疑 `truncateMessages(..., 6000)` 在 256k 上下文时代太短，要求调研成熟系统（Claude Code、Codex）的做法。

---

### 问题发现

用户原话："智能截断6000 是不是太短了啊! 现在大模型上下文都 256k上下文了"

具体症状：
1. `aiService.ts` 中 `truncateMessages(messages, 6000)` — 硬编码，所有模型一视同仁
2. `messages.slice(-10)` — 只保留最近 10 条消息
3. `ModelConfig` 没有 `contextWindow` 字段
4. 截断标记只是 `... [内容已截断]` — AI 不知道自己被截断了
5. 工具层面无限制，`getArticleContent` 一次返回全文

**关联历史**：此问题为新增，之前未处理过上下文截断策略。

---

### 调研过程

通过 Web Search 检索了 5+ 来源：

| 系统 | 核心策略 | 来源 |
|------|---------|------|
| Claude Code | 三级压缩：Microcompact → Full Compact(LLM摘要) → Trim Fallback | cave-agent PyPI 文档 |
| OpenAI Codex | 工具输出硬限制 256行/10KiB + 90%窗口触发自动压缩 | GitHub issue #6426, Codex 源码分析 |
| VS Code Copilot | `SimpleSummarizedHistory` 文本摘要 + `PrioritizedList` | deepwiki 分析 |
| Cline | 保留初始消息 + 模型感知截断 + 成对删除 | cline.bot 博客 |
| CaveAgent | 受 Claude Code 启发的三级压缩，含熔断机制 | PyPI 文档 |

**核心洞察**：所有成熟系统都截断，但做法是**分层+透明+可续读**。不是"要不要截"，是"怎么做"。

---

### 方案选择与对比

| 方案 | 优点 | 缺点 | 决策 |
|------|------|------|------|
| A. 全部不截 | 信息完整 | 请求可能爆炸 | ❌ 放弃 |
| B. 固定 128k 上限 | 简单 | 8k/16k 小模型会崩溃 | ❌ 放弃 |
| C. LLM 摘要历史（Claude Code Tier 2）| 最智能 | 实现复杂，额外成本 | ⏳ 未来做 |
| D. 三级智能截断+工具源头控制 | 模型感知、可续读、工程务实 | 标记文字占 token | ✅ 采用 |

**选择 D 的原因**：
- Codex 和 Claude Code 都在工具层面做限制（源头控制）
- 截断标记必须让 AI 感知（Codex 用 `[omitted ...]`）
- Token 估算是基础（Claude Code 显示实时用量）

---

### 尝试但失败的方案

**尝试 1：完全移除截断，依赖模型自身**
- 思路：256k 模型够大，日常用不完
- 放弃原因：用户说"抓一个 10MB 网页怎么办"——工具输出可能无限长，必须有一道保险

**尝试 2：只按 token 预算截断，不区分工具类型**
- 思路：所有消息同等对待，按比例截断

**尝试 3：在 `messages.slice(-10)` 处改为动态计算保留条数**

- 放弃原因：更好的做法是完整传入所有消息，让 `smartTruncateMessages` 在 token 层面决定保留多少。按"条数"截断不如按"token 预算"截断精准。

## 任务 8：Claude Code Skill 系统源码分析

**时间**：2026-04-18 会话末尾
**触发**：用户质疑 MetaBlog 当前 `skillMatcher` 前端自动注入 LOD-2 不是真正的"渐进式披露"，要求研究 Claude Code 源码。
**本地源码**：`D:\ALL IN AI\claude-code-rev-main`

---

### 核心发现：Claude Code 的 Skill 模型是"Agent 主动调用工具"，不是"前端预注入"

#### 1. System Prompt 中只放 Skill Catalog（目录）

文件：`src/utils/attachments.ts` 第 2661-2751 行

`getSkillListingAttachments()` 函数每轮对话生成一个 `skill_listing` attachment：
- 内容格式：`- name: description`（只有名称+简短描述）
- Token 预算限制：仅占 context window 的 1%（约 8k 字符）
- 去重机制：`sentSkillNames` Set 跟踪已发送过的 skill，避免重复注入
- 被渲染为 system reminder：`The following skills are available for use with the Skill tool:\n\n{content}`

```typescript
// src/utils/messages.ts:3728-3737
return wrapMessagesInSystemReminder([
  createUserMessage({
    content: `The following skills are available for use with the Skill tool:\n\n${attachment.content}`,
    isMeta: true,
  }),
])
```

**关键**：System Prompt 里只有 skill 的名称和描述，**没有完整内容**。

#### 2. Skill 是一个普通工具（`SkillTool`）

文件：`src/tools/SkillTool/SkillTool.ts`

工具定义：
```typescript
export const SkillTool: Tool = buildTool({
  name: SKILL_TOOL_NAME, // 'Skill'
  description: async ({ skill }) => `Execute skill: ${skill}`,
  inputSchema: z.object({
    skill: z.string().describe('The skill name. E.g., "commit", "review-pr", or "pdf"'),
    args: z.string().optional().describe('Optional arguments for the skill'),
  }),
  // ...
})
```

工具 prompt（`src/tools/SkillTool/prompt.ts` 第 173-196 行）：
```
Execute a skill within the main conversation

When users ask you to perform tasks, check if any of the available skills match.

When users reference a "slash command" or "/<something>", they are referring to a skill. Use this tool to invoke it.

How to invoke:
- Use this tool with the skill name and optional arguments
- Examples:
  - `skill: "pdf"` - invoke the pdf skill
  - `skill: "commit", args: "-m 'Fix bug'"` - invoke with arguments

Important:
- Available skills are listed in system-reminder messages in the conversation
- When a skill matches the user's request, this is a BLOCKING REQUIREMENT: invoke the relevant Skill tool BEFORE generating any other response about the task
- NEVER mention a skill without actually calling this tool
```

**关键**：Agent 在 system prompt 里看到 skill 目录后，**自己判断**是否需要调用某个 skill，然后主动发起 `SkillTool` 调用。

#### 3. Skill 调用后的展开：注入 `newMessages` 到后续对话

文件：`src/tools/SkillTool/SkillTool.ts` 第 580-840 行（`call` 方法）

执行流程：
1. Agent 调用 `SkillTool` 传入 `{skill: "commit"}`
2. `validateInput` 验证 skill 存在且可用
3. `call()` 方法内部：
   - 找到对应的 Command（skill）
   - 调用 `processPromptSlashCommand(commandName, args, commands, context)`
   - 内部通过 `getMessagesForPromptSlashCommand` 展开 skill 的完整 prompt
   - 返回 `{ data: {...}, newMessages: [...], contextModifier: fn }`
4. `newMessages` 被注入到后续对话上下文中
5. 通过 `addInvokedSkill` 注册，**保证 compaction 后 skill 内容不丢失**

```typescript
// 返回值结构
return {
  data: { success: true, commandName, allowedTools, model },
  newMessages,  // ← skill 完整内容作为新消息注入
  contextModifier(ctx) { /* 更新允许的工具列表、模型覆盖 */ }
}
```

**关键**：skill 的完整内容是在 Agent **主动调用**后才被注入的，不是一开始就塞进 system prompt。

#### 4. 两种执行模式

| 模式 | 触发条件 | 实现 | 用途 |
|------|---------|------|------|
| **Inline**（默认） | `command.context !== 'fork'` | `newMessages` 注入主对话 | 简单 skill，直接扩展 prompt |
| **Forked** | `command.context === 'fork'` | `runAgent()` 启动子 agent | 复杂 skill，独立 token 预算 |

Forked 模式（第 122-289 行）：在隔离的 sub-agent 中执行 skill，有自己的 token 预算和工具集，结果提取后返回主对话。

#### 5. `discover_skills` 是可选的 feature flag 功能

文件：`src/tools/DiscoverSkillsTool/`
- 仅在 `EXPERIMENTAL_SKILL_SEARCH` feature flag 开启时可用
- 用于 Agent **搜索远程 skill**（AKI/GCS 上的 canonical skills）
- 普通本地 skill 不需要 discovery，因为 `skill_listing` 已经包含了所有可用 skill

#### 6. 与 MetaBlog 当前模式的对比

| 维度 | Claude Code | MetaBlog 当前 |
|------|-------------|---------------|
| System Prompt 中的 skill 内容 | 只有名称+描述（catalog） | 完整 skill markdown（LOD-2） |
| 谁决定加载哪个 skill | **Agent 主动判断** → 调用 `SkillTool` | **前端 `skillMatcher` 关键词匹配** → 自动注入 |
| Skill 内容何时注入 | Agent 调用 `SkillTool` 后 | 每轮对话开始时（预注入） |
| Agent 选择权 | ✅ 有（可以决定不调用 skill） | ❌ 无（被动接受匹配结果） |
| Token 控制 | 目录受 1% budget 限制，内容按需加载 | 所有匹配 skill 的完整内容一次性注入 |
| 远程 skill 支持 | `discover_skills`（feature flag） | 无 |
| Skill 持久化 | `addInvokedSkill` + compaction 保护 | 无（每次重新匹配） |

---

### 结论

用户的质疑是**正确的**：MetaBlog 当前 `skillMatcher.ts` 前端关键词匹配 + 自动注入 LOD-2 确实**不是** Claude Code / Codex 的"渐进式披露"模式。

Claude Code 的真正模式是：
1. **System Prompt 只放 Catalog**（LOD-0 级别）
2. **Agent 有选择权**——自己判断是否需要 skill
3. **Agent 主动调用工具**——`SkillTool` 加载 skill
4. **Skill 内容按需注入**——通过 `newMessages` 展开到后续对话
5. **Compaction 保护**——已调用 skill 的内容持久化到对话状态

这是真正的"渐进式披露"：信息按需加载，Agent 有决策权，不是前端包办。

---

### MetaBlog 改造方向（待决策）

如要迁移到 Claude Code 模式，需要：
1. **移除** `skillMatcher.ts` 的自动 LOD-2 注入逻辑
2. **新增** `loadSkill` 工具（类似 Claude Code 的 `SkillTool`）
3. **改造** `promptBuilder.ts`：System Prompt 只放 catalog（LOD-0），不放完整内容
4. **新增** 对话状态跟踪：`loadedSkills` Set（per-turn，不是全局）
5. **新增** skill 调用后的展开机制：将 skill markdown 内容转为 `newMessages` 注入上下文
6. **可选** `discover_skills` 工具（如果未来支持远程 skill）

**工作量估算**：约 2-3 天（涉及对话状态管理、工具定义、prompt 构建逻辑重构）。

**决策阻塞**：用户需确认是否进行此架构改造。当前模式（前端匹配+预注入）虽然不够"渐进式"，但实现简单、确定性高。Claude Code 模式更优雅但更复杂，需要 Agent 有更强的判断能力。

### System Prompt 核心缺陷（用户提出）

**问题**: Agent 的 System Prompt 虽然列出了 Skills 和工具名称，但**完全没有告诉 LLM 它可以调用工具**，也不知道怎么调用。

**根因分析**:
1. `agentStore.ts` 的 `buildSystemPrompt` **从未调用** `buildToolsDescription()`，LLM 看不到完整工具列表
2. System Prompt 没有说明 Function Calling 的工作机制（`tool_calls` 输出、`tool` 角色消息返回）
3. `loadSkill` 的说明只是 JSON 示例，没有明确这是 function call
4. **更严重**：`buildSystemPrompt` 函数赋值了 `fullPrompt` 变量但**没有 `return` 语句**！函数实际上返回 `undefined`

**尝试的修复**: 重写 `buildSystemPrompt` 为字符串数组 `join` 方式：
- 明确声明 Function Calling 能力
- 调用 `buildToolsDescription()` 列出所有工具
- 详细说明工具调用流程
- 强调 `loadSkill` 是第一入口
- 提供完整工作流程示例

**遇到的阻塞**: 模板字符串中存在 Markdown 代码块反引号（`` ``` ``）和 Unicode 箭头（`→`），导致 `vue-tsc` 报 `Invalid character`。改用字符串数组 `join` 方式重构时，`StrReplaceFile` 多次匹配失败（长文本 + Unicode 字符），替换工作未完成。
