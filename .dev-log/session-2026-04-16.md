### 问题 2：页面莫名其妙刷新，导致对话丢失

- **现象**：AI 调用 `create_article` 等工具后，整个页面被强制刷新（`full-reload`）。
- **根因分析（第一轮）**：`server/routes/content.ts` 中写文件 API（create/update/delete/move）在成功后会调用 `triggerReload()`，通过 Vite websocket 发送 `type: "full-reload"`，浏览器整页刷新，SPA 内存状态全丢。
- **修复（第一轮）**：将 `content.ts` 中 5 处 `triggerReload()` 调用注释掉。
- **复发**：用户反馈页面仍然会被刷新。
- **根因分析（第二轮）**：
  1. `server/routes/init.ts` 中还有 5 处 `triggerReload()` 调用，对应 `/api/save`、`/api/files/rename`、`/api/files/move`、`/api/files/delete`、`/api/files/restore`。这些 API 也可能被 AI 工具间接调用。
  2. **更重要的根因**：VitePress dev server 本身会监听 `docs/` 目录下的 `.md` 文件变化。当 AI 工具创建/修改文章时，VitePress 的 markdown HMR 机制会**自动触发 full-reload**。这与我们的 `triggerReload()` 是独立的两个来源。
- **修复（第二轮）**：
  1. 将 `init.ts` 中 5 处 `triggerReload()` 全部注释掉。
  2. 将 `server/vitepress-integration.ts` 中 `triggerReload` 的实现改为空操作（只打印日志，不再发送 `full-reload` websocket 消息）。
  3. 在 `metaBlogBffPlugin` 中新增 Vite `handleHotUpdate` 钩子，拦截 `docs/` 目录下 `.md` 文件的 HMR，返回空数组以阻止 VitePress 自动 full-reload。
- **修改文件**：
  - `server/routes/init.ts`
  - `server/vitepress-integration.ts`
- **状态**：✅ 已修复，但需要用户**硬刷新页面（Ctrl+F5）**使新代码生效

## 新增任务：Article Creator（自动叶子节点提升）（自动叶子节点提升）

### 需求来源

用户提出："目前的创建文章工具创建 md 的时候是不会检测它是不是叶子节点的"。如果 AI 创建文章时不考虑现有 folder-note 结构，可能会破坏项目的文档树规范。用户还询问了性能问题，并提出了 lazy/delay 创建的设想。

### 方案分析与设计

**关于 lazy/delay 创建**：

- 经过分析，**不需要 delay**。
- `fs.existsSync` 在本地 SSD 上耗时 < 1ms，路径检测是 O(深度) 的，通常只有 1~3 级。
- Node.js 的 `fs.promises.writeFile` 是 awaitable 的，文件落盘是立即可见的。
- AI 工具调用在前端是**顺序执行**的（`aiService.ts` 的 `while` 循环是 `await` 的），不存在并发竞态。
- Delay 反而会给 AI 和用户带来"已创建但未可见"的不确定性。

**真正的问题**：

1. 前端 `create_article` 工具的 executor 直接调用 `/api/files/save`，**完全绕过了**后端的 folder-note promotion 逻辑。
2. 后端 `/api/articles/create` 虽然有 promotion 逻辑，但要求 AI 显式传入 `isChildDoc` 和 `parentPath`，这增加了 AI 决策负担。
3. 现有后端的 promotion 逻辑把原文件移到 `index.md`，而 `doc-structure.ts` 的 preferred 模式是 `folder/folder.md`，存在不一致。

**最终方案**：

1. 新建 `server/utils/article-creator.ts`：统一创建入口，做**路径感知的自动 promotion**。
   - 接收 `section + title + 可选 path`
   - 逐级检查路径上的每一级目录
   - 如果发现某级是叶子文档（如 `A.md` 存在但 `A/` 不存在），自动提升为 folder-note（`A/A.md`）
   - 然后原子性写入目标文件
2. 修改 `/api/articles/create`：调用 harness，简化接口参数。
3. 修改 `create_article` 工具：走 `/api/articles/create`，移除 `isChildDoc` / `parentPath` 参数。

### 实现细节

**`server/utils/article-creator.ts`**：

- `promoteLeafToFolderNote(leafPath)`：将 `A.md` 提升为 `A/A.md`
- `createArticleInHarness(req)`：
  - 解析 `path`（如 `posts/attention/flash-attention.md`）
  - 对每一级中间目录做 `existsSync(leafPath) && !existsSync(folderPath)` 检测
  - 如有冲突，自动 promotion
  - 最后写入文件，返回 `{ path, action, promotedNodes }`

**修改的文件**：

- `server/utils/article-harness.ts`（新建）
- `server/routes/content.ts`（重写 `/api/articles/create`，使用 harness）
- `src/theme/tools/article/definitions.ts`（简化 `create_article` 参数定义）
- `src/theme/tools/article/executors.ts`（`create_article` 改为调用 `/api/articles/create`）

### 性能评估

- 典型创建操作：2~6 次 `fs.existsSync` + 1 次 `fs.mkdir` + 1 次 `fs.writeFile`
- 总耗时：< 10ms（本地文件系统）
- 结论：性能完全不是瓶颈，无需 lazy/delay 或缓存层

## 任务：修复多轮工具调用卡死 + 恢复流式 Markdown 实时渲染

### 用户反馈

1. "markdown 要实时渲染的" —— 之前为性能在流式时跳过 `marked.parse`。
2. "连续调用 10+ 工具就会卡死" —— 从截图看，工具调用行能正常显示，但底部卡在"AI 思考中"，最终回复没有出来。

### 根因分析

#### 1. DeepSeek API 是否有问题？

新建了测试脚本 `model-reference/deepseek/test-multi-round-tools.ts`，直接调用 DeepSeek API（`deepseek-reasoner`）进行 12+ 轮工具调用 + 思考模式测试。

**测试结果**：API 本身正常完成 13 轮（12 轮 tool_call + 1 轮最终回复），没有挂起。
- 工具调用轮：2~8s 完成
- 最终回复轮：60+s，返回 2000+ chars，766 个 chunks

**结论**：DeepSeek API 不会"卡死"，但最终回复的流确实比较慢（60s+）。

#### 2. 前端为什么卡死？

两个叠加的性能陷阱：

**陷阱 A：`chatStore.ts` 的 `onContent` 每个 SSE chunk 都更新 Vue reactive**
- 最终回复有 766 个 chunks，在 60s 内平均约 80ms 一个 chunk
- 每个 chunk 都执行 `targetMsg.content = text`，触发整个消息列表的 reactive 更新和 diff
- 即使 markdown parse 被 throttle，Vue 的 render + diff 仍然被调用数百次

**陷阱 B：`MessageBubble.vue` 的 `watch(timelineItems)` 每次都重建 `expandedItems`**
- `timelineItems` 是 computed，返回新数组引用
- 每次 `onThinkingStep` push 新元素，`watch` 都触发，创建全新的 `expandedItems` 对象
- 导致 `v-for` 中的 key/expansion 状态频繁变动，DOM 操作暴增

### 修复方案

**修复 1：恢复流式 Markdown 实时渲染（带 throttle）**
- 文件：`src/theme/components/ai-chat/MessageBubble.vue`
- 将 `renderedHtml` 从 `computed` 改为 `ref` + `watch`
- 非流式：立即 parse
- 流式：120ms throttle，避免 `marked.parse` 的 O(n²) 重复调用

**修复 2：消除 `expandedItems` 的频繁重建**
- 文件：`src/theme/components/ai-chat/MessageBubble.vue`
- `watch(timelineItems)` 中只在新 item 的 id 首次出现时写入 `expandedItems`
- 保留用户已手动切换的状态

**修复 3：给 SSE 流增加连接/idle 超时保护**
- 文件：`src/theme/api/services/aiService.ts`
- `connection timeout`：30s 内未建立连接则主动 abort
- `idle timeout`：60s 内未收到任何 chunk 则主动 abort
- 防止浏览器 fetch 无限挂起

**修复 4：给 `onContent` 回调增加 80ms throttle**
- 文件：`src/theme/api/services/aiService.ts`
- `chatStreamInternal` 内累积 content，每 80ms 最多调用一次 `callbacks.onContent`
- 在 `[DONE]` 或流结束时强制 `flushContent(true)`，确保最终文本不丢失
- 这样前端重渲染频率从 ~600 次/分钟降到 ~80 次/分钟

## 任务：定位"10 次工具调用后卡住"的根因

### 日志分析

查看 `.logs/2026-04-16.jsonl` 发现：

1. 后端在 round 10 正常记录 `tool_call_complete`，随后记录 `message_complete (77525ms)`
2. 但**紧接着用户又发了几乎完全相同的消息**，说明前端没有看到最终回复
3. 第二次对话同样在 round 10 后 `message_complete (79241ms)`，用户又第三次重发

### 根因确认

问题在 `src/theme/api/services/aiService.ts` 的 `chatStream` 方法中：

```typescript
while (hasMoreToolCalls && toolRound < maxToolRounds) {
  toolRound++
  // ... 执行工具调用 ...
  if (!toolCalls || toolCalls.length === 0) {
    callbacks.onComplete()
    return { toolRecords }
  }
}
// while 结束后：
// 只记录了日志，**从未调用 callbacks.onComplete()**
```

当 AI 在第 10 轮仍然返回 `tool_calls` 时：
- 工具执行完毕后 `toolRound == 10`，`toolRound < maxToolRounds` 条件不满足
- while 循环直接退出
- 前端 `chatStore.ts` 的 `onComplete` **从未被触发**
- 消息状态永远停留在 `streaming`，UI 永远显示"AI 思考中"

这就是"一旦到 10 次就卡了"的**真正根因**。

### 修复方案

1. **while 循环结束后强制调用 `callbacks.onComplete()`**
2. **达到 `maxToolRounds` 时，自动追加一轮不带 tools 的 final request**，把已收集的工具结果强制总结为最终回复，避免用户看到空白
3. **`maxToolRounds` 默认值从 `10` 提升到 `15`**，给复杂任务更多容错空间
