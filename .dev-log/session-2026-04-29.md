## 任务 15：修复微信图片防盗链导致 processImage/ocrImage 失败

### 问题发现

用户截图显示：`processImage` 调用微信文章中的图片链接 `https://mmbiz.qpic.cn/...` 时返回 `Failed to fetch`。

用户原文：「这是自动从微信文章内容拿到图片链接自动读取然后工具不支持这个链接了吗」

### 根因分析

微信图片服务器（`mmbiz.qpic.cn`）有**防盗链机制**：
1. **Referer 校验**：图片请求必须携带 `Referer: https://mp.weixin.qq.com/`，否则返回 403
2. **CORS 限制**：前端 `fetch` 跨域请求时，微信服务器不设置 `Access-Control-Allow-Origin`，浏览器会拦截响应

当前 `processImage` 和 `ocrImage` 都是**前端工具**，直接 `fetch(imageUrl)`：
- 对于普通图片（无防盗链）→ 正常工作
- 对于微信/知乎等防盗链图片 → 前端 fetch 被拦截 → `Failed to fetch`

**关于链接不一致**：
用户提到文章内容中的图片链接和 AI 调用的链接不是同一个。这是因为微信文章中通常有多张图片，AI 可能选择了不同的图片进行识别。这不是 bug，但防盗链问题会同时影响所有微信图片链接。

### 方案选择

**方案 A**：告诉用户"微信图片不支持"。
- Cons：用户体验极差，微信是最主要的内容来源之一。

**方案 B**：后端创建图片代理 `/api/image-proxy`，前端工具 fetch 失败时自动 fallback。
- Pros：对用户完全透明，任何防盗链图片都能自动处理。

**选择 B**。

### 实现过程

1. **创建后端代理 `server/routes/internal/image-proxy.ts`**
   - 接口：`GET /api/image-proxy?url=<图片URL>`
   - 用 Node.js `https` 模块请求图片（Node.js 不受浏览器 CORS 限制）
   - 自动根据域名设置 Referer：
     - `mmbiz.qpic.cn` → `https://mp.weixin.qq.com/`
     - `zhimg.com` → `https://zhuanlan.zhihu.com/`
   - 返回图片二进制流 + 正确的 Content-Type
   - 安全限制：仅支持已知防盗链域名或图片后缀名

2. **修改 `ocrImage` 工具**（`src/theme/tools/platform/generic.ts`）
   - fetch 图片时加 try/catch
   - 直接 fetch 失败 → 自动 fallback 到 `/api/image-proxy?url=xxx`
   - 获取 blob 后继续走原有 `/api/ocr` 流程

3. **修改 `processImage` 工具**（同上文件）
   - HEAD 请求失败时同样 fallback 到代理

4. **路由注册**
   - `server/routes/index.ts` 导出 `registerImageProxyRoutes`
   - `server/vitepress-integration.ts` 在 `registerOCRRoutes` 之后注册

### 修改文件清单

|------|---------|------|
| `server/routes/internal/image-proxy.ts` | 新增 | 后端图片代理服务 |
| `server/routes/index.ts` | 更新 | 导出 image-proxy 路由 |
| `server/vitepress-integration.ts` | 更新 | 注册 image-proxy 路由 |
| `src/theme/tools/platform/generic.ts` | 更新 | ocrImage 和 processImage 支持代理 fallback |

### 验证结果

- `npx tsc --noEmit --skipLibCheck` → 无编译错误 ✅
- 代码逻辑审查：fetch 失败时 catch 捕获 → 调用代理 → 代理设置正确 Referer → 返回图片流 → 前端获取 blob → 传给 OCR。链路完整。

### 是否复发

## 任务 4：后端自动 OCR 注入（文章内联图片处理）

## 任务 6：方案 B 完整实施 — Kimi 通过 file_id 看文章原图

### 问题发现

用户选择"死磕方案 B"，要让 vision 模型（Kimi）真正能"看"到文章中的原图，而不是仅靠 OCR 文字。

### 根因分析

1. Kimi API **不支持远程图片 URL**（官方文档明确 `URL-formatted images: Not supported`）
2. Kimi API **支持 file_id 引用**（`ms://file_id` 协议）
3. Kimi API 请求体有 **100MB 硬限制**（base64 方式受限）
4. 当前工具调用结果以文本形式返回，无法直接承载二进制图片数据给 vision 模型

### 方案设计

**核心思路**：后端下载图片 → 上传到 Kimi 获取 file_id → Markdown 中图片 URL 替换为 `ms://file_id` → 消息层识别 `ms://file_id` 并转成 `image_url` 内容部分

**优势**：
- file_id 只是字符串引用，不占请求体空间，不受 100MB 限制
- 消息层自动转换，对 AI 透明
- 同时保留 Markdown 文本（带行号）和图片原图

### 实现过程

1. **新增 Kimi 文件上传服务** `server/services/kimi-file-upload.ts`：
   - `uploadFileToKimi(filePath, purpose)`：上传单个文件到 Kimi API
   - `uploadImagesToKimi(filePaths, maxConcurrent)`：批量上传图片，并发 3
   - 自动读取 `LLM_KIMI_API_KEY` / `KIMI_API_KEY` 环境变量
   - 超时 60 秒，错误处理完善

2. **平台解析层增强** `server/routes/platform/`：
   - `types.ts`：`ParseResult` 新增 `imageFiles?: Array<{file_id, url}>`，`ParseOptions` 新增 `fetchImageFiles?: boolean`
   - `parser.ts`：
     - 新增 `addLineNumbers()`：给 Markdown 每行加行号（`1 | 内容`）
     - 新增 `fetchImageFilesForVision(content, images)`：下载图片 → 上传 Kimi → 替换 Markdown 中的图片 URL 为 `ms://file_id`
     - `parseHtmlToMarkdown` 集成：先 OCR/上传 → 最后统一加行号

3. **前端消息层增强** `src/theme/api/services/aiService.ts`：
   - 新增 `extractMsFileIds(content)`：从文本中提取 `ms://file_id`
   - `convertMessageToApiFormat()` 末尾增加检测：如果消息内容包含 `ms://file_id` 且模型支持 vision，自动把 file_id 转成 `{type: 'image_url', image_url: {url: 'ms://file_id'}}` 附加到 content 数组

4. **前端工具增强** `src/theme/tools/platform/generic.ts`：
   - `parsePlatformLinkDef` 增加 `fetch_image_files` 参数
   - description 更新，明确 embed_ocr / fetch_image_files 二选一

5. **错误翻译增强** `server/routes/internal/chat.ts`：
   - 新增 413 错误码翻译：`Payload Too Large` → "请求体过大，建议减少图片数量或改用 file_id"

6. **Skill 更新** `.skills/content-analyst/SKILL.md`：
   - 工作流 B 更新：vision 模型传 `fetch_image_files=true`，非 vision 传 `embed_ocr=true`
   - 明确二选一，不要同时传

### 修改文件清单

| 文件 | 修改类型 | 说明 |
|------|----------|------|
| `server/services/kimi-file-upload.ts` | 新增 | Kimi 文件上传服务，获取 file_id |
| `server/routes/platform/types.ts` | 修改 | ParseResult 增加 imageFiles，ParseOptions 增加 fetchImageFiles |
| `server/routes/platform/parser.ts` | 修改 | addLineNumbers、fetchImageFilesForVision、集成到 parseHtmlToMarkdown |

### 验证结果

- `npx tsc --noEmit --skipLibCheck` 通过，0 错误
- 修复了 `generic.ts` 中模板字符串嵌套反引号的问题

### 使用方式

**非 vision 模型（DeepSeek）**：
```typescript

// 返回：带行号的 Markdown，OCR 文字嵌入在图片下方
```

**vision 模型（Kimi）**：
```typescript
parsePlatformLink(url="...", extract_images=true, fetch_image_files=true)
// 返回：带行号的 Markdown，图片 URL 已替换为 ms://file_id
```

### 遗留问题

1. **Kimi file_id 有效期**：官方文档未明确 file_id 有效期，可能是一次性的或短期有效。如果对话跨会话，file_id 可能失效。
2. **图片上传失败降级**：如果某张图片上传 Kimi 失败，当前只是跳过该图片。后续可考虑降级为 OCR。
3. **最大图片数限制**：`MAX_VISION_IMAGES = 10`，如果文章超过 10 张图，后面的图不会被上传。Kimi 实际支持更多图片，但受 token 限制。

## 任务 18：修复微信文章正文缺失 + AI 传错参数

### 问题发现

用户原话：「readArticle 正文什么都没」「为什么发给 kimi k2.5 会调用 OCR」「我原来直接用 fetchUrl 都能拿到正文的」。

现象：
- `readArticle(url=微信链接, fetch_image_files=true)` 返回的 content 只有一行提示文字："Yingweimei 机器之魂 继续滑动看下一个 机器之魂 向上滑动看下一个"
- 标题正确、作者正确、图片 URL 正确，但正文完全缺失
- 第一次调用时 AI 传了 `embed_ocr=true`（非 vision 路径），后来才传对 `fetch_image_files=true`
- `method` 字段保持为 `"wechat"`，没有被任何解析步骤覆盖

### 根因分析

**根因 1：L4 DOM 选择器正则无法处理嵌套标签**
```
regex = /<[^>]*id="js_content"[^>]*>([\s\S]*?)<\/[^>]+>/i
```
`[\s\S]*?` 是非贪婪匹配，遇到第一个 `</...>` 就停止。`#js_content` 内部有大量嵌套 `<div>`/`<section>`，正则只匹配到第一个子元素的结束标签（~97 字符），导致正文被截断。

**根因 2：Readability.js 在用户的环境中静默失败**
- 我的本地测试显示 Readability.js 能正确提取 2761 字符正文
- 但用户实际环境中 `method` 保持为 `"wechat"`，说明 Readability.js 没有成功（抛异常或返回空内容）
- `catch { /* ignore */ }` 导致失败原因被吞掉

**根因 3：`method` 变量被 `fetcherMeta.method` 污染**
`method` 初始值是 `"wechat"`，后续步骤使用 `method = method || "xxx"`，由于 `"wechat"` 不是 falsy，`method` 永远不会被覆盖为实际的解析方法名。

**根因 4：system prompt 未明确告诉 AI 它是 vision 模型**
`readArticle` description 让 AI 根据"是否是 vision 模型"选择参数，但 system prompt 中没有明确声明。AI 第一次默认走了 `embed_ocr=true`（非 vision 安全路径）。

### 方案选择

**方案 A**：只修复正则，其他不管。
- Cons：Readability.js 失败的问题没解决，method 记录仍错误。

**方案 B**：全面修复 fetch + parse + prompt。
- `fetcher.ts`：微信增加 Playwright 兜底（绕过反爬）
- `parser.ts`：L4 改用 jsdom querySelector（正确处理嵌套），修复 method 记录，增加日志
- `agentStore.ts`：根据 `agent.runtime.model` 显式声明 vision/text 能力
- `generic.ts`：简化 `readArticle` 参数选择描述

**选择 B**。

### 实现过程

1. **`server/routes/platform/fetcher.ts`**：`WechatFetcher` 改用 Playwright 兜底
   - 先尝试 HTTP fetch
   - 检测反爬特征（`环境异常`、`完成验证`）→ 自动 fallback 到 Playwright
   - 检测正文缺失（无 `js_content` 或 `rich_media`）→ 也 fallback

2. **`server/routes/platform/parser.ts`**：L4 DOM 选择器改用 jsdom
   - 优先用 `doc.querySelector(selector)` 获取 `innerHTML`
   - 增加 `innerHTML.trim().length > 50` 过滤，避免匹配到空壳元素
   - jsdom 失败后再回退到正则
   - 新增 `extractMethod` 变量，独立于 `fetcherMeta.method`
   - 所有 `method = method || "xxx"` 改为 `extractMethod = extractMethod || "xxx"`

3. **`src/theme/stores/agentStore.ts`**：system prompt 声明模型能力
   - 导入 `modelSupports` 函数
   - `buildSystemPrompt` 中根据 `agent.runtime?.model` 判断 vision 能力

4. **`src/theme/tools/platform/generic.ts`**：简化参数选择描述

## 任务 21：聊天消息气泡支持 LaTeX 公式与图片代理显示

### 问题发现

### 方案选择

**方案 B**：后端保留 `ms://file_id` 供 vision 使用，但不再替换 `content` 中的 URL（content 保留原始 URL 供前端显示），同时后端提供 `/api/image-proxy` 供前端加载图片，前端 marked 渲染时自动重写图片 URL 走代理。

1. **安装依赖**
   - `katex@0.16.21` — KaTeX 渲染引擎
   - `marked-katex-extension@5.1.8` — marked 的 KaTeX 扩展

2. **后端 `/api/image-proxy`（proxy.ts）**
   - 复用现有 `registerProxyRoutes`，新增 `/api/image-proxy` 路由
   - `GET /api/image-proxy?url=xxx`
   - 自动根据域名设置 Referer：
     - `mmbiz.qpic.cn` / `mp.weixin.qq.com` → `https://mp.weixin.qq.com/`
     - `zhimg.com` → `https://zhuanlan.zhihu.com/`
   - 透传 Content-Type，返回图片二进制流
   - Cache-Control: `public, max-age=3600`

3. **修改 `fetchImageFilesForVision`（parser.ts）**
   - 保留上传 Kimi 获取 file_id 的逻辑（供 vision 使用）
   - **删除** content 中图片 URL 替换为 `ms://file_id` 的逻辑
   - 返回 `{ content: 原始content, imageFiles: 上传结果 }`

4. **前端 `MessageBubble.vue`**
   - 导入 `katex/dist/katex.min.css`
   - 导入 `marked-katex-extension`，`marked.use(markedKatex({ throwOnError: false, nonStandard: true }))`
   - 自定义 `marked.Renderer().image`：把 `href` 重写为 `/api/image-proxy?url=<encodeURIComponent(href)>`
   - 添加 `.response-body :deep(img)` 样式：`max-width: 100%`、`border-radius: 10px`
   - 添加 `.response-body :deep(.katex)` / `:deep(.katex-display)` 样式
