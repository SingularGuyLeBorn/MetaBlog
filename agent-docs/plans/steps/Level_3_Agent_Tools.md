# Step 3: AI 的 Agent 化改造 (接入 Tools)

## 1. 概念定位
这一步是传统 LLM 走向 Agent（智能体）的跨越时刻。AI 原本只是一个陪聊的语言模型，在完成了 Agent 化改造后，我们让后端解析大模型的意图（Function Calling / Tools Use），赋予其“双手”，使其能够真实操作第一步（Step 1）构建的本地系统 API 以及外部互联网 API，完成真正的「代为操作」。

## 2. 核心功能点与状态
- **功能 1：工具定义与抽象层 (Tool Registry)**
  - **描述**：将传统的 JS 函数封装成符合规范的 JSON Schema（名称、描述、入参结构）。
  - **完成度**：✅ `100% 已实现`
  - **说明**：系统内已有如 `get_current_time`, `read_file`, `write_file`, `web_search` 等标准 Tools 定义。
- **功能 2：意图拦截与函数调用链 (Function Execution Loop)**
  - **描述**：当大模型回复不是普通文本，而是“需要调用 `read_file` 查阅 A 文件”时，服务端负责拦截该指令，自动本地执行该工具代码，并将结果(Result)扔回给大模型进行第二次思考总结。
  - **完成度**：✅ `100% 已实现`
  - **现有交互**：此过程对后端静默，对前端而言，UI 上会显示一个“Thought：正在读取文件 xxx”的过渡态卡片，增加系统运转的可观测性。
- **功能 3：工具鉴权与安全锁**
  - **描述**：执行如 `删除文件` 这样高危且直接的操作时，确保只授权给特定的模式。
  - **完成度**：⚠️ `部分完成`（代码里有 `allowedTools` 数组限制，但缺少严格防呆确认）。

## 3. UI 交互设计剖析
- **UI 组件层：Trace/Thought 渲染器**：
  - **表现**：在 AI 聊天瀑布流的 Message 组件中，当识别到大模型返回的是 Tool Call 块时。插入一个特殊的 UI 组件 `<TraceNode />` 或类似的玻璃态执行胶囊。
  - **动效**：显示 ⏳ `[正在执行: 搜索网络 (keyword="VitePress 侧边栏")]`。执行返回结果后，变为 ✅ `[执行完毕 104ms]` 并在悬浮提示中可以点击展开折叠的详细 JSON Return 数据。
  - **目的**：通过“透明计算”打消用户焦虑，也就是咱们常说的“白盒化运行过程”。

## 4. 内部链路与流转规约 (Function Loop)
大模型 (如 Deepseek) <----> Express Backend

1. **Input**: 前端发送 `{ text: "今天有什么科技新闻" }` 经 API 发往后端。
2. **Backend -> LLM**: 组装 `msgs` 连同所有注册的 `tools` Schema，向 LLM 建立连接。
3. **LLM -> Backend**: LLM 决定调用，返回 `{ "tool_calls": [{"name": "web_search", "args": {"query": "tech news today"}}] }`。
4. **Backend Local**: 后端挂起请求，阻断向前端的消息直出。本地寻找注册表内的 `web_search` 代码块执行，可能耗时 2 秒，得到长文本结果。
5. **Backend -> LLM**: 将执行结果以 `{ role: 'tool', content: '新闻列表...' }` 形式连同之前的上下文再次送入 LLM。
6. **LLM -> Frontend**: LLM 阅读了结果，开始流式输出最终人类能懂的 Markdown 总结给到最终端。

## 5. 缺陷与演进建议
1. **缺陷**：目前所有定义的工具是一股脑儿塞给 AI 的。当工具数量超过 30 个甚至 100 个时（比如涵盖绘图、邮件、全项目遍历等），不仅拖死 Context 长度，更会导致大模型产生“幻觉”选错工具。
2. **演进目标**：为第四步的 **Agent 管理中心** 埋下伏笔。必须要能做到：为不同的 Agent “按需分配”特定的 Tools 子集，避免过载。这就是为什么要进入下一等级的根本原因。
